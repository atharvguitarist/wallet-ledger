Setup (both sessions): `SET search_path = isolation_lab;` wallets 10 (Asha, ₹500 = 50000 paise) and 20 (Rahul, ₹300).

### Case 1 — Read Committed (the Postgres default)
```
A=> BEGIN;  -- READ COMMITTED
BEGIN
A=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 50000  
B=> UPDATE wallets SET balance = balance - 10000 WHERE id = 10;
UPDATE
B=> -- (autocommit: committed immediately)
A=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 40000  
A=> COMMIT;
COMMIT
```
**Result:** yes — session A sees a different value (50000, then 40000) inside the same transaction. Each statement in Read Committed takes a fresh snapshot: a *non-repeatable read*.

### Case 2 — Repeatable Read
```
A=> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
A=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 50000  
B=> UPDATE wallets SET balance = balance - 10000 WHERE id = 10;
UPDATE
B=> -- committed
A=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 50000  
A=> -- now try to write based on what A read:
A=> UPDATE wallets SET balance = balance - 5000 WHERE id = 10;
ERROR:  could not serialize access due to concurrent update
A=> ROLLBACK;
ROLLBACK
A=> SELECT balance FROM wallets WHERE id = 10;  -- outside any transaction
 balance
---------
 40000  
```
**Result:** session A keeps seeing 50000 for the whole transaction: its snapshot is taken at the first query and never moves. When A then tries to update the row that B changed, Postgres refuses with *could not serialize access due to concurrent update* (SQLSTATE 40001) instead of silently losing B's update. The application must retry.

### Case 3 — Serializable: both sessions read a balance, then write based on it
```
A=> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
B=> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
A=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 50000  
B=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 50000  
A=> -- A spends ₹100: 50000 - 10000
A=> UPDATE wallets SET balance = 40000 WHERE id = 10;
UPDATE
B=> -- B also spends ₹100 based on the 50000 it read (this statement blocks on A's row lock...)
B=> UPDATE wallets SET balance = 40000 WHERE id = 10;
B   ...waiting...
A=> COMMIT;
COMMIT
B   ERROR:  could not serialize access due to concurrent update  (SQLSTATE 40001)
B=> ROLLBACK;
ROLLBACK
A=> SELECT balance FROM wallets WHERE id = 10;
 balance
---------
 40000  
```
**Result:** one of them fails. B waits for A's row lock; when A commits, B is aborted with SQLSTATE 40001. Without that error B would have written 40000 too and one ₹100 spend would vanish (a lost update). Serializable makes this safe, but the losing transaction must be retried by the application.

#### Case 3b (bonus) — Serializable catches write skew on *different* rows
Rule: Asha + Rahul together must keep at least ₹700. Each session checks the total, then debits a *different* wallet.
```
A=> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
B=> BEGIN ISOLATION LEVEL SERIALIZABLE;
BEGIN
A=> SELECT sum(balance) AS total FROM wallets;
 total
-------
 80000
B=> SELECT sum(balance) AS total FROM wallets;
 total
-------
 80000
A=> UPDATE wallets SET balance = balance - 10000 WHERE id = 10;
UPDATE
B=> UPDATE wallets SET balance = balance - 10000 WHERE id = 20;
UPDATE
A=> COMMIT;
COMMIT
B=> COMMIT;
ERROR:  could not serialize access due to read/write dependencies among transactions
```
**Result:** no row was written twice, so row locks would not help — yet Serializable (SSI) still aborts the second commit with *could not serialize access due to read/write dependencies among transactions*. Repeatable Read would have let both commit and broken the ₹700 rule.

### Case 4 — Repeatable Read with a join
```
A=> BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN
A=> SELECT u.name, w.balance FROM wallets w JOIN users u ON u.id = w.user_id WHERE w.id = 10;
 name | balance
------+---------
 Asha | 50000  
B=> BEGIN;
BEGIN
B=> UPDATE users SET name = 'Asha V.' WHERE id = 1;
UPDATE
B=> UPDATE wallets SET balance = balance - 10000 WHERE id = 10;
UPDATE
B=> COMMIT;
COMMIT
A=> SELECT u.name, w.balance FROM wallets w JOIN users u ON u.id = w.user_id WHERE w.id = 10;
 name | balance
------+---------
 Asha | 50000  
A=> COMMIT;
COMMIT
A=> SELECT u.name, w.balance FROM wallets w JOIN users u ON u.id = w.user_id WHERE w.id = 10;
 name    | balance
---------+---------
 Asha V. | 40000  
```
**Result:** yes, the guarantee holds across the join. The snapshot belongs to the *transaction*, not to a table, so every table in every query sees the database as of A's first statement. Only after COMMIT does A see "Asha V." and 40000.


## Summary

| Case | What session A saw | Anomaly prevented? |
|---|---|---|
| 1. Read Committed | 50000 then 40000 in one transaction | No: non-repeatable read |
| 2. Repeatable Read | 50000 both times; its write to the changed row failed with 40001 | Yes, by snapshot + "concurrent update" error |
| 3. Serializable, same row | B blocked on A's lock, then failed with 40001 | Yes: lost update prevented, B must retry |
| 3b. Serializable, different rows | second COMMIT failed with 40001 (read/write dependencies) | Yes: write skew prevented |
| 4. Repeatable Read + join | old name and old balance across both tables | Yes: one snapshot for the whole transaction |

## Which level does the transfer use, and why?

The money path ([`src/services/transfers.js`](../src/services/transfers.js)) runs at **READ COMMITTED with explicit row locks**:

1. `SELECT … FROM accounts WHERE id = $1 FOR UPDATE`, one row at a time in ascending id order;
2. re-check the balance on the locked row;
3. insert the transfer and its two ledger lines, update both balances;
4. `COMMIT`.

That is enough because the only shared state a transfer *decides* on is the balance of the rows it locks. Once a transfer holds `FOR UPDATE` on a wallet, any other transfer from that wallet waits at its own `SELECT … FOR UPDATE` until the first commits, and then reads the new balance (in Read Committed a statement that waited for a row lock re-reads the latest committed version). So two transfers can never both spend the same rupee. The stampede test proves this: 100 concurrent ₹10 transfers from ₹500 gives exactly 50 successes, 20 runs out of 20.

Why not Serializable?

- **Retries.** Under contention many transactions fail with `40001` and must be retried in full. In the stampede, with Serializable and no locks, every request that read the balance before another committed would be aborted and have to start again; with `FOR UPDATE` they simply queue and each runs once.
- **Throughput.** SSI tracks read sets (predicate locks) for every transaction, which costs CPU and memory and produces false-positive aborts on hot tables like `transfers`.
- **Write skew isn't our risk.** Serializable earns its keep in case 3b, when a decision depends on rows you do *not* write. Our invariant ("this wallet ≥ 0") lives on the row we lock and write, and it is also a CHECK constraint. The fraud rules read other rows (recent transfers of the same wallet), but they run *after* that wallet's row is locked, so every transfer from that wallet is serialized behind the lock anyway.

The code still retries on `40001`/`40P01` (serialization failure, deadlock) as a safety net, but lock ordering means deadlocks shouldn't happen.

One place uses **Repeatable Read** on purpose: the nightly reconciliation, because all five checks must see the same snapshot while transfers keep committing.
